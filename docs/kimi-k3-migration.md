# Kimi-K3移行設計メモ

（PM 作成 2026-07-30、同日 v2 更新。原本は PM の個人ノート。検討中。
実測データとの突合注記は末尾「実測との突合（2026-07-30 追記）」を参照）

[[Argus]] の推論モデルを GLM-5.2 から [[Kimi-K3]] へどう組み込むかの設計検討。2026-07-30時点。

## 結論

**単純な差し替えでは効果が出ない。GLM-5.2は捨てず、役割分担にする。**

GLM-5.2とKimi-K3の差は文脈長ではない（どちらも1Mトークン）。差は3点に集約される。

1. **ネイティブ視覚** — GLM-5.2は text-in/text-out で視覚を持たない
2. **長時間自律** — 長い綱で自分で判断し続けるタスクで2〜3倍の差
3. **preserved thinking history** — 思考履歴の往復が前提。実装対応が必須

したがってArgusで効くのは Pass 1（文書を画像で読む）と Pass 3（エージェントの綱を長くする）の2箇所。抽出プロンプトの差し替えではほぼ何も変わらない。

**ただし理研の推論ゲートウェイに約600秒のタイムアウトがあり、これが設計を強く縛る。**「1回の巨大呼び出し」型の設計は取れない。詳細は後述。

## 理研（RIKYU）とハードウェア要因

[[RIKYU]] は GB200 NVL4 × 400ノード（Blackwell GPU 1,600基、FP8で15.5 EFLOPS超）。K3のMXFP4重みは約1.4〜1.5TBなので2〜4ノードで載る。**規模は制約にならない。**

さらに重要な点：**BlackwellはFP4をテンソルコアでネイティブに扱う**ので、K3の量子化形式がそのままハードウェアの得手バスに乗る。

- K3：活性104B を FP4 で
- GLM-5.2：活性40B を BF16 で（MITだが量子化は自前）

活性パラメータは2.6倍だが、FP4はBF16に対して理論4倍のスループット。**トークン単価はむしろK3の方が安い可能性がある。**「大きいモデルだから遅い」という先入観で設計判断してはいけない。まず実測すること。

Argusは既に aarch64 運用（`~/.venv_aarch64/`）なので、Grace CPUとの整合が取れており移植の摩擦はない。

## 最大の制約：nginx 約600秒タイムアウト

理研の推論ゲートウェイ（nginx）に約600秒の制限がある。**規模やコストではなく、これが設計上いちばん厳しい制約。** K3は思考を無効化できず `max` effortでは数万トークン思考しうるため、GLM-5.2より当たりやすい。

### まず種類を見分ける

nginxの `proxy_read_timeout` は**バイト間の無通信時間**を計る。種類によって対策が正反対になる。

| 種類 | 対策 |
|---|---|
| `proxy_read_timeout`（無通信600秒） | **ストリーミングで解決する。** トークンが流れ続ける限りタイマーがリセットされる |
| ロードバランサ等の絶対上限600秒 | ストリーミングでは解決しない。リクエスト自体の分割が必須 |

**判定方法** — 合計900秒かかるが常時トークンが流れるリクエストをストリーミングで投げる。通れば無通信タイムアウト、切れれば絶対上限。**他の検討の前にこれを確定させる。**

### K3特有の落とし穴

**K3は `reasoning_content` を先に出す。** サービング側が思考部分をバッファして完了まで送らない実装だと、`max` effortで数万トークン思考が溜まると無通信になり、`stream: true` にしても切れる。**理研の推論スタックが `reasoning_content` をトークン単位でストリームするかを必ず確認する。**

### 600秒はリクエスト上限であってセッション上限ではない

エージェントループは多数のリクエストの連鎖なので、各ターンが600秒未満なら100ターンでも通る。**長時間自律（優先度3）は成立する。** 危険なのは「1回の巨大呼び出し」型の設計（旧・優先度4）。

### 運用側への打診

600秒はチャット用途の想定値で、エージェント用途を想定していない設定の可能性が高い。**タイムアウト緩和、またはnginx迂回の直接経路を打診する価値がある。**

## 提案

### 優先度1：APIクライアント層を作り直す

以下4点は**すべて同じコードパス**（`scripts/argus/pm_argus_agent.py`、`scripts/argus/agent_tools.py`）なので、個別対応ではなくAPIクライアント層の再設計として一度にやる。これを直さないと以降の提案がすべて目減りする。

**(a) `reasoning_content` を往復させる**

K3は preserved thinking history モードで訓練されている。**マルチターン・ツール呼び出しでAPIが返した assistant メッセージを `reasoning_content` と `tool_calls` ごとそのまま `messages` に戻す必要がある**。`content` だけ拾って再構成すると、マルチステップ調査が静かに劣化する。

**(b) ストリーミングを既定にする**

`stream: true` を全経路で既定に。nginx 600秒（無通信タイムアウトだった場合）への一次防御。`reasoning_content` がトークン単位で流れてくることが前提に絡む。

**(c) 逐次永続化する**

600秒で切られると生成中の出力と**思考トレースがまるごと消える**。preserved thinking mode では思考の喪失が通常より痛い。ストリームで受けたトークンを `reasoning_content` を含めて逐次DBへ書く。

**(d) partial mode で再開する + ツールを冪等にする**

切断されたら partial mode（assistantメッセージに既得分をプリフィルして継続）で再開する。K3はpartial modeをサポートしている（ただし理研のvLLM/SGLang経路で露出しているか要確認）。あわせて全ツールを冪等にし、リトライで pm.db に二重書き込みが起きないようにする。

### 優先度2：Pass 1 — 文書をMarkdownに落とすのをやめる

現状 `pm_box_crawl.py` は pptx/docx/pdf/xlsx をMarkdown化し、`slide_ocr.py` はスライドをOCRしている。**この2工程が情報を捨てている。** ガントチャート、矢印つき構成図、体制図、ダッシュボードのスクショ、セル結合された表 — 富岳NEXTの進捗資料でPM上いちばん重要な部分がテキスト化で失われうる。

- pptx/pdf をページ画像にレンダリングしK3に直接渡す
- `box_docs.db` にページ画像パス列を追加
- **Markdownは残す**（FTS5索引の資産なので捨てない）。二系統で持つ
- relevance判定（core/related/noise）を視覚込みで行う
- 議事録生成でもWhisper文字起こし + VTT話者情報 + **スライド画像そのもの**を同時に渡す。OCRテキスト経由をやめる

GLM-5.2では原理的に不可能だった経路。**「他モデルで代替できない」という意味で最も価値が高い。**

対象：`scripts/data-pipeline/pm_box_crawl.py`、`scripts/data-pipeline/pm_box_relevance.py`、`scripts/recording/slide_ocr.py`、`scripts/recording/generate_minutes_local.py`

### 優先度3：Pass 3 — エージェントの綱を長くする

Patrol Agentは30分cronで固定4項目（完了シグナル・期限超過・停滞・健全性）を回している。これは短い決め打ちタスクで、K3の強みが出ない設計。

- 固定チェックの30分cronはそのまま軽量モデルに残す
- **週1回、常設セッション型の長時間セッションを別に立てる**
  例：「pm.db・議事録DB・Box資料を全部読み、M3の遅延リスクを自分で定義して調査し、根拠つきで報告せよ」
  ターン上限100+
- `/argus-investigate` のステップ数上限を大幅に緩める

SWE-Marathon / AutomationBench の2〜3倍差は、まさにこの「長い自律セッション」の差。

**600秒制約への配慮（1ターンを短く保つ）** — セッションは長く、各ターンは短く。

- **effortと思考量の積を管理する。** 文脈が大きいターンでは `max` を避け `high` に落とす。無条件の `reasoning_effort=max` は危険
- 1ターンあたりの `max_tokens` を保守的に設定し、足りなければ次ターンに渡す
- **ツール呼び出しを細かく刻む。** 1ツールあたりの返却量を絞れば次ターンのプリフィルも軽くなる

対象：`scripts/argus/pm_argus_patrol.py`、`scripts/argus/pm_argus_agent.py`

### 優先度4：Pass 1 と Pass 2 の統合（※600秒制約により方式を修正）

狙いは変わらない。`enrich_items.py` が別パスでやっている突合（重複排除、status遷移、根拠補完）を抽出と同時に実行し、さらに**2ヶ月前の決定との矛盾検出**まで行う。READMEの「同じ議論が繰り返される」「合意が形骸化する」に直接効く。

> **「1Mに全部載せる」設計は却下**
> 当初は「会議録 + 過去3ヶ月の関連アクション + `goals.yaml` + 関連Box資料を1回の推論に載せる」案だったが、**600秒制約下ではそれが最も危険な設計**。巨大プリフィル + 長い思考 + 大きな出力を1リクエストに集約するので真正面からタイムアウトに当たる。

**採用する方式：共通prefixをキャッシュし、多数の中規模呼び出し**

- `goals.yaml` + マイルストーン定義 + ツールスキーマ + システムプロンプトを context caching のprefixに固定（毎回同一なので効く）
- 本体は会議単位・週単位に窓分割
- 300K前後で文脈圧縮を挟む
- FTS5 + bge-m3 のハイブリッド検索は捨てない。「検索で絞ってから広く載せる」構成を維持

Moonshot自身がBrowseCompで1M全投入（90.4）より**300Kで文脈圧縮を挟んだ方が高スコア（91.2）**だった。**タイムアウト対策と精度が同じ方向を向いている**点で、制約を飲んでも損がない珍しいケース。

### 優先度5：ハイブリッド・ルーティング

どちらも同じ基盤でサービングされているので、ハイブリッド構成の運用コストはゼロ。**置き換えではなく役割分担。**

| 経路 | モデル | 理由 |
|---|---|---|
| Slack差分トリアージ、relevance判定、`/argus-today` | GLM-5.2 `high` | 活性40Bがテキストで足りる。思考をOFFにできる |
| 議事録生成、Box資料の読解 | **Kimi-K3 `high`** | 視覚必須。GLM-5.2では原理的に不可能 |
| 抽出＋マイルストーン紐づけ＋矛盾検出 | Kimi-K3 `high` | 1M文脈でPass 1+2統合 |
| `/argus-investigate`、週次深掘り | **Kimi-K3 `max`** | 長時間自律で2〜3倍差 |
| embedding | bge-m3 のまま | 変更不要 |

**GLM-5.2を捨てる工程は一つもない。**

### 優先度6：既存MCP資産をそのまま活かす

K3はMCP経路が最強（MCPMark-Verified 94.5で全モデル中トップ、MCP-Atlas 84.2、Toolathlon-Verified 76.5）。すでに `pm_mcp_server.py` がFastMCPで全ツールを出しているので、**オーケストレータをClaude CodeからKimi Code CLIに差し替えるだけ**で長時間セッションを回せる。追加実装ほぼゼロ。

あわせて：

- **context caching** — `goals.yaml` + マイルストーン定義 + ツールスキーマ + システムプロンプトは毎回同一。prefixに固定する
- **dynamic tool loading** — 15ツールをフェーズ別に絞る

## 残る制約

**nginx 約600秒。** 上記の専用セクション参照。最も厳しい制約であり、優先度1と優先度4の設計を規定している。

**常駐エンドポイントの確保。** Patrol Agentは30分cron、`/argus-brief` はSlackの3秒応答制約がある。理研が共有クラスタ機である以上、「Slack botのために2〜4ノードを24時間占有」するのは割当ポリシーの問題。**キュー待ち時間の実測が先にいる。** ここが詰まると設計以前に使えない。

**常時thinkingのコスト。** K3は思考をOFFにできないので、高頻度パスに流すと共有サービスのトークン消費が跳ねる。ハイブリッド・ルーティングでGLM-5.2を残す理由の半分はこれ。

**ライセンス。** MIT から Kimi K3 License への変更が生じる。既に理研でサービングしているなら機関として通っている可能性が高いが、念のため確認。

## 実測との突合（2026-07-30 追記、v2 対応。Argus 側評価データより）

本メモの方向性を docs/decisions/rikyu_argus_model_eval.md の実測（one-shot 2×2 検証ほか）と突合した注記。

**実測が支持する点**:
- 「役割分担・GLM は捨てない」— brief/risk/today 系は glm-5.2 が品質・速度・JSON 安定性で最良（実測済み）。glm-oneshot は search 型 investigate で現行比 83.3% 勝ち・31s
- 「1M 全部載せは却下、検索で絞ってから広く載せる」— N スイープで N=50（≈50k 字）が N=200/600 と同品質・最速を実測。one-shot 経路（broad-recall + 1 回渡し）は v2 優先度 4 の方式そのもの
- 「600 秒はリクエスト上限でありセッション上限ではない」— k3-loop（多ターン）は 8 問完走・forced synthesis ゼロを実測。1 呼び出しの長考（salmon 問 one-shot N=200/600）だけが 504 で全損した

**ストリーミング仮説について（重要・当方の観測の訂正込み）**:
- **当方が観測した 504（~600s、計 4 回）はすべて非ストリーミング呼び出し**。本番経路 `call_argus_llm` の local ルートは `no_stream=True` 固定（llm.py）で、評価もこの経路を通った。つまり「無通信タイムアウトならストリーミングで解決する」という v2 の仮説は**当方のデータと完全に整合し、未検証のまま残っている**。ステップ0 の判定プローブが最優先で正しい
- 過去に「client --timeout では回避不可」と記録したが、これは非ストリーミング前提の観測。ストリーミングで回避できる可能性は排除されていない

**実測が補正する点**:
- **`reasoning_effort` は RIKYU 配信の K3 では効かない**（low/high/max の 3 手段すべて無効を実測。effort=low で reasoning がむしろ増加）。v2 優先度 3 の「effort と思考量の積を管理」は、現状のサービングでは **effort ノブが機能しない**前提で、max_tokens とタスク分割側で管理する必要がある。effort が効くかどうか自体もステップ0 系のプローブに含めるべき（サービング更新で変わりうる）
- investigate では現行ループ + K3（k3-loop）より **one-shot + K3 の方が品質同等以上・レイテンシ 1/3**（gold 8 問実測）。「綱を長くする」は preserved thinking 対応（優先度 1a）とセットで初めて意味を持つ見込み
